# 0002. «ИИ понимает, движок планирует»

- Статус: предложено
- Дата: 2026-11-21

## Контекст

Маршрут обязан гарантированно включать обязательные пожелания туриста (`JOL_SSOT.md §2` п.3,
`§4`) и укладываться в бюджет поездки с учётом жилья (`§5.2`), а также учитывать погоду (`§7`),
память (`§8`) и бесплатность для пользователя (`§2` п.1). Провайдер LLM не выбран
(`§14`, `§16.12`). LLM по природе недетерминирован и может «забыть» пожелание или
ошибиться в арифметике бюджета.

## Решение

Разделение ответственности (`TECH_PLAN.md §3`):

- **LLM (за интерфейсом `LLMProvider`)** делает только то, что требует понимания языка:
  извлекает параметры поездки (даты, бюджет, жильё, пожелания, стиль, темп, отношение к людям — `§4`),
  сжимает ввод в тезисы для графа (`§11.2`), объясняет готовый план.
- **Детерминированный `planner` на сервере** строит маршрут: выбор мест, раскладка по дням, время,
  бюджет и жильё (ночи × цена за ночь, `§5.2`), транспорт между точками (`§5.3`).
  Результат LLM-ем не правится; на вход planner получает структурированный `trip_brief`.
- Обязательные пожелания добавляются в план в первую очередь; если выполнить нельзя — флаг
  `must_have_unmet` и честное сообщение, а не молчаливая подмена (`TECH_PLAN.md §2` п.11).
- Превышение бюджета обрабатывает planner (`§5.2` п.4), LLM лишь формулирует предупреждение.

## Последствия

- Гарантии (must-have, бюджет) проверяются обычными тестами, не промптами.
- Провайдера LLM можно сменить адаптером; в dev работает заглушка.
- Planner — дополнительный объём серверного кода и данных (время посещения, цены, часы работы).
- Живой план (`§7`) пересчитывает тот же planner, а не LLM; изменения оформляются как предложения.
- Качество разговора зависит от LLM, качество маршрута — от данных и алгоритма.
