# 0003. Значения по умолчанию для открытых вопросов SSOT §16

- Статус: предложено (все пункты ждут подтверждения владельца)
- Дата: 2026-11-21

## Контекст

В `JOL_SSOT.md §16` есть открытые вопросы, от которых зависит код. Работать молча по догадке
нельзя, стоять — тоже. `TECH_PLAN.md §0 п.4` требует расширяемую заготовку с поведением по
умолчанию. Ниже — допущения из `TECH_PLAN.md §2`. Все — **[предложено]**; они не являются
продуктовыми решениями.

## Решение

| SSOT §16 | Вопрос | Поведение по умолчанию в коде [предложено] |
|---|---|---|
| 1 | Кто делает готовые маршруты для гостей (§3.1) | Команда вручную: таблица `curated_routes`, ввод через админку |
| 2 | Валюта бюджета (§4) | Только тенге (`*_kzt`, целые); при вводе в другой валюте ИИ переспрашивает сумму в тенге |
| 3 | Превышение бюджета (§5.2) | Показываем оба варианта (убрать места / дешёвые альтернативы), выбирает пользователь |
| 4 | Изменения по погоде (§7.1) | Только с подтверждением: «предложение изменения», применяется по кнопке |
| 5 | Загруженность (§7.3) | Собственные данные: «я здесь» + отчёты «людно/пусто» |
| 6 | Офлайн-карта (§7.4) | Не в v1; скачиваются только данные маршрута |
| 7 | Оплата и комиссия (§9, §12) | Оплаты в приложении нет; бронирование = запрос партнёру / внешняя ссылка |
| 8 | Формула бонусов (§10.3) | Заглушка в одном модуле `bonus_policy.py`, коэффициенты в таблице |
| 9 | Пометка рекламы (§5.1) | Метка «Реклама» / «Ad» на карточке промо-мероприятия |
| 10 | Финансирование (§12) | Не влияет на код |
| 11 | Нет партнёра под обязательное пожелание (§12) | Этап 1: все места на карте, проблемы нет; флаг `must_have_unmet` + честное сообщение ИИ |
| 12 | Провайдер LLM / SMS (§14) | Интерфейсы `LLMProvider` / `SmsProvider`; в dev заглушки, реальный провайдер — адаптером |
| 13 | Серверный стек (§14) | Python 3.12 + FastAPI (см. ADR 0001) |

В брифе пожелание остаётся, полная пересборка вернёт его. Ш-38 |

| Правка маршрута: что пересчитывается | Только день правки: остановки остаются в прежнем порядке, переходы строятся заново, время идёт подряд с начала дня; остальные дни и весь планировщик не трогаются. Замена: кандидат из категории / по названию / по id, берётся первый, после которого день без потерь; иначе 409 `no_replacement`. Выбранные человеком виды транспорта для неизменных пар «откуда–куда» сохраняются. Ш-38 |

Одно ожидающее предложение на поездку (следующее — после ответа; после принятия ставится внешний re-check). Предложение, составленное для прежней версии плана, устаревает: `expired`, accept даёт 409 `proposal_stale`. Ш-40 |
| Погода: «день страдает» | Только для outdoor-остановок типа `activity` (не обед). Часы визита: гроза (WMO 95/96/99) в любом часу; иначе не менее 50 % известных часов с дождём (вероятность >= 0,6), ветром >= 40 км/ч или жарой >= 35 °C. Порядок: гроза, дождь, ветер, жара. Часы без прогноза игнорируются. Порог дождя 0,6 выше планировочных 0,5 намеренно: план, построенный при 0,5, не дёргается от колебаний прогноза. Константы в `app/live/rules.py`. Ш-40 |

Прогноз при сборке: `build_trip` берёт его у `app.state.weather_provider`; сбой = план без прогноза. Ш-40 |

Один раз на поездку и день (`trip_day_notices`). Для гор строже: ветер >= 30 км/ч и мороз <= 0 °C на высоте места. Сообщение только о погоде (лавины, тропы, закрытия не учитываются). Если прогноза нет, задача повторяется с отсрочкой; сообщения «прогноза нет» нет. Ш-40 |
| Пуши | Исходящие в таблице `push_notifications` (пишутся в той же транзакции, что сообщение и предложение), доставка задачей `push.send` вне транзакции; по устройствам пользователя (`devices.user_id`, есть `apns_token`); `delivered_to` исключает повтор после сбоя; токен, отвергнутый APNs (410 / BadDeviceToken), стирается. `POST /v1/devices` без токена доступа привязывает устройство ни к кому (вышедшее устройство не получает чужих пушей). Провайдер по умолчанию `log` (ничего не шлёт); `apns` нужны `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY` (платный аккаунт Apple не заведён: разрыв в ключах). Ш-40 |
| Память: штраф за отвергнутый тип (SSOT §8) | Считается при чтении из `user_place_signals` (отдельной таблицы `user_category_affinity` нет: нет второй копии, формулу можно менять без миграции). Удаление = 0,30, замена = 0,20 на категорию; вес вдвое затухает за 120 дней; штраф не выше 0,6 (пол веса 0,4): в скоринге это минус не более `W_MEMORY * 0,6` = 1,2 очка при интересе 3 и популярности до 2. Типы показываются реже, не исчезают; обязательные пожелания не скорятся и всегда попадают в план. Читаются последние 300 сигналов. Ш-41 |
| Память: избранное в скоринге (SSOT §11.5) | Избранное место +0,8, место из категории, где есть избранное, +0,3 (не суммируются); мало по сравнению с интересом (3). Скрытые/закрытые избранные не считаются. Ш-41 |
| Память: заметки (SSOT §8) | `user_memory_notes`: одна заметка на чат (обновляется), не более 600 символов, одной строкой; хранятся 8 новейших на пользователя. Пишет LLM задачей `memory.note` (внешняя, без транзакции): через 2 минуты после сборки маршрута (чтобы в чате уже было объяснение) и `memory.scan` раз в час для чатов, молчащих более 6 часов (не старше 30 дней, не меньше 4 сообщений, без свежей заметки). В чат заметки и категории попадают отдельным сообщением `<user_memory_data>` (экранировано, обрезано, помечено как данные), не в системный промпт. Гостям память не пишется и не читается. Ш-41 |
| Скачанный маршрут: формат и ETag (SSOT §7.4) | `GET /v1/trips/{id}/offline`: дни со временем, места по id (один раз), для перехода выбранный вид и геометрия (polyline6). ETag = `"v<version>-<язык>"`, `If-None-Match` -> 304 (после проверки владельца). Правка данных места без новой версии маршрута (часы, адрес) в ETag не отражается: клиент обновляет копию при смене версии. Фото-превью `photo_url` = `MEDIA_BASE_URL/<storage_key>`, пока переменная пуста (до Ш-44) — null. Ш-42 |
| Очередь задач: аренда | Захват задачи отдельной короткой транзакцией: `locked_at` (аренда и токен владельца), `attempts + 1`; аренда 300 с (`WORKER_LEASE_SEC`) не продлевается; истёкшая аренда = задача доступна снова, исчерпавшая попытки гибнет; завершение только владельцем аренды; `payload` стирается при завершении (done / dead). Обработчики с внешними вызовами (`external=True`) не держат транзакцию, доставка at-least-once, они идемпотентны. Ш-06 (правки) |
| Refresh-токен: повтор (Ш-43) | Семейство = строка `sessions`; заменённые хеши лежат в `session_retired_tokens`. Повтор заменённого токена позже 10 с (`REUSE_GRACE_SECONDS`) отзывает всю сессию; в пределах 10 с это гонка двух обновлений: 401 без отзыва. Ш-24 №1 |
| Хранилище фото (Ш-44) | S3-совместимое, загрузка по presigned PUT (SigV4, адресация path-style, подписаны `Content-Type` и `Content-Length`), чтение и удаление сервером. В dev — `STORAGE_PROVIDER=local` (диск + `PUT /v1/dev-uploads`, раздача `/media`), только `dev`/`test`. Публичный URL = `MEDIA_BASE_URL/<storage_key>`; ключ случайный (`ugc/ГГГГ/ММ/<uuid>.ext`), без id пользователя. Лимиты: JPEG/PNG/WebP, 8 МБ, 40 загрузок и 30 отправок в сутки на человека |
| Проверка изображения (Ш-44) | Сервер читает загруженный объект один раз при отправке: размер равен заявленному, магические байты (JPEG/PNG/WebP) равны заявленному типу, считается sha256 (дубликаты). Не проверяется: декодирование, EXIF/GPS (убирает клиент), содержимое картинки |
| Отзывы и контент: видимость (SSOT §10.2) | Прошедшее автофильтр = `published_pending_review`: отзыв и фото видны сразу с пометкой «проверится позже» (`pending_review`). Меню, цены и данные о транспорте до одобрения модератором к месту не применяются (они перезаписали бы факты); одобренное меню заменяет `place_menu` (источник `user`), цена для `adult` обновляет `entry_price_kzt` и защищает его от импортёра (`manual_override`), данные о транспорте только помечаются одобренными. Один отзыв на человека и место (в приложении, не в схеме) |
| Удаление аккаунта и пользовательский контент (Ш-44) | По образцу `place_photos.author_user_id`: опубликованное (`published_pending_review`, `approved`) остаётся обезличенным (`user_id` = NULL, `author_name` = null); неопубликованное (`rejected_auto`, `rejected`), слоты загрузок и их файлы удаляются (файлы задачей `storage.delete`). Текст отзыва переживает аккаунт; убрать его может модератор |
| Автофильтр (Ш-45) | Правила без LLM: длина отзыва от 10 символов, повторы, ссылки и контакты, мат-лист RU/EN/KZ (`submissions/profanity.txt`, зачаток), дубликаты текста и фото (sha256), правдоподобие цен (вход до 200 000 ₸ и в 10 раз от известной цены, блюдо 50–100 000 ₸, проезд до 5 000 ₸). Любое срабатывание = `rejected_auto` (ответ 201 с `reason_codes`, бонуса нет, файл удаляется). Классификация LLM не сделана |
| Бонусы: временная формула (SSOT §10.3, §16.8) | Бонус = базовая сумма по типу (отзыв 20, фото 50, меню 100, цена 40, транспорт 60) × коэффициент давности (поле старше 180 дней и больше → ×2, свежее → ×0,5, данных нет → ×2) × коэффициент частоты (поездок с местом за 90 дней: 0 → ×1, 20 и больше → ×2). Транспорт без множителей. Константы в `demand_coefficients`, правятся в админке «Бонусы», запасные значения в `bonus_policy.py`. Платится один раз после одобрения модератором (`idempotency_key = submission:<id>`), отклонённое и отсеянное автофильтром — 0. Потолок 100 000 на отправку. Нет: суточного лимита, трат. `bonus_ledger` только вставки (триггер), уходит вместе с аккаунтом (`ON DELETE CASCADE`): тратить пока нечего, это личные данные. Ш-46 |
| Обратное геокодирование (Ш-23c, SSOT §6.1, §13) | `GET /v1/geocode/reverse`: ближайшее активное место в 30 м, иначе ближайший адрес или именованное здание из `osm_addresses` в 50 м (точка = центр здания), иначе точка. Только свои данные, внешние геокодеры не вызываются. Вне границ Алматы — 422. Лимит 120 запросов в минуту на адрес клиента, `Cache-Control: public, max-age=300`. Ш-23c |
| Одноразовый код: неверный и просроченный (Ш-25) | `otp_invalid` — есть действующий код и догадка неверна (попытка считается); `otp_expired` — угадывать нечего (кода нет, истёк, использован, попытки исчерпаны). Неизвестный адрес получает `otp_expired`: ответ не раскрывает, есть ли аккаунт. `429 otp_rate_limited` несёт `Retry-After` в секундах |
| Очистка (Ш-44) | Задача `retention.cleanup` раз в час: просроченные слоты загрузок (кроме `used`) и их файлы (через `storage.delete`), `session_retired_tokens` старше 60 дней |
| Загруженность места (§16.5, Ш-47) | Отчёт принимается от вошедшего пользователя в радиусе 200 м. Пять отчётов за 60 дней открывают статистику места, два в одном местном часу недели дают оценку этого часа. Вес уменьшается вдвое за 14 дней. Для дневного маршрута нужны пять дневных отчётов. |
| Промо-мероприятия (§16.9, Ш-48) | В указанные даты карта и чат получают подпись «Реклама» или «Ad» для продвигаемого мероприятия. У общедоступных достопримечательностей и государственных объектов рекламное размещение запрещено. |
| Бронирования (§16.7, Ш-49) | Карточка предлагает поддерживаемые виды брони только при наличии активной связи места с партнёром и доступного адаптера. Для разработки используется тестовый партнёр. Подключение реальных партнёров и условия оплаты требуют решения владельца. |

### Соглашение о комментариях в коде

Каждое место, где реализовано допущение по открытому вопросу, помечается комментарием
`# OPEN(SSOT §16.N)` (N — номер вопроса), например `# OPEN(SSOT §16.4)`. В Swift и SQL —
тем же текстом с синтаксисом комментария языка: `// OPEN(SSOT §16.4)`, `-- OPEN(SSOT §16.4)`.
Так все допущения находятся одним поиском `OPEN(SSOT §16.` по репозиторию. Когда владелец решает вопрос: сначала правится `JOL_SSOT.md`
(с записью в журнале §17), затем код, и комментарий убирается.

## Последствия

- Разработка не блокируется открытыми вопросами, а заготовки легко заменить.
- Есть риск, что решение владельца будет отличаться; цена — переделка локальной заготовки.
- Шаги плана, упирающиеся в открытый вопрос, могут получать статус `[!]` (`TECH_PLAN.md §0` п.3).
- Пока ADR в статусе «предложено», строки таблицы обновляются при закрытии вопроса. После
  принятия ADR — по правилам `README.md`: изменение оформляется новым ADR «заменяет 0003».
