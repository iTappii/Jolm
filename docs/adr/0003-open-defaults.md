# 0003. Значения по умолчанию для открытых вопросов SSOT §16

- Статус: предложено (все пункты ждут подтверждения владельца)
- Дата: 2026-11-21

## Контекст

В `JOL_SSOT.md §16` есть открытые вопросы, от которых зависит код. Работать молча по догадке
нельзя, стоять — тоже. `TECH_PLAN.md §0 п.4` требует расширяемую заготовку с поведением по
умолчанию. Ниже — допущения из `TECH_PLAN.md §2`. Все — **[предложено]**; они не являются
продуктовыми решениями.

## Решение

| SSOT §16 | Вопрос | Поведение по умолчанию в коде [предложено] |
|---|---|---|
| 1 | Кто делает готовые маршруты для гостей (§3.1) | Команда вручную: таблица `curated_routes`, ввод через админку |
| 2 | Валюта бюджета (§4) | Только тенге (`*_kzt`, целые); при вводе в другой валюте ИИ переспрашивает сумму в тенге |
| 3 | Превышение бюджета (§5.2) | Показываем оба варианта (убрать места / дешёвые альтернативы), выбирает пользователь |
| 4 | Изменения по погоде (§7.1) | Только с подтверждением: «предложение изменения», применяется по кнопке |
| 5 | Загруженность (§7.3) | Собственные данные: «я здесь» + отчёты «людно/пусто» |
| 6 | Офлайн-карта (§7.4) | Не в v1; скачиваются только данные маршрута |
| 7 | Оплата и комиссия (§9, §12) | Оплаты в приложении нет; бронирование = запрос партнёру / внешняя ссылка |
| 8 | Формула бонусов (§10.3) | Заглушка в одном модуле `bonus_policy.py`, коэффициенты в таблице |
| 9 | Пометка рекламы (§5.1) | Метка «Реклама» / «Ad» на карточке промо-мероприятия |
| 10 | Финансирование (§12) | Не влияет на код |
| 11 | Нет партнёра под обязательное пожелание (§12) | Этап 1: все места на карте, проблемы нет; флаг `must_have_unmet` + честное сообщение ИИ |
| 12 | Провайдер LLM / SMS (§14) | Интерфейсы `LLMProvider` / `SmsProvider`; в dev заглушки, реальный провайдер — адаптером |
| 13 | Серверный стек (§14) | Python 3.12 + FastAPI (см. ADR 0001) |

### Допущения вне нумерации §16

| Тема | Поведение по умолчанию [предложено, ждёт владельца] |
|---|---|
| Максимальная длительность поездки (в SSOT не задана) | 60 дней (`MAX_TRIP_DAYS` в `server/app/chat/brief.py`) — техническая граница от мусорного ввода, не продуктовое правило. Ш-31, 2026-11-21 |
| Ёмкость и расписание дня по темпу (в SSOT не заданы) | `calm` 10:00–20:00, 3 активности; `normal` 09:30–21:00, 4; `dense` 09:00–22:00, 6 (+ обед и ужин каждый день); гора = 2 активности. Обед с 12:00 до 14:30 (60 мин), ужин с 18:00 до 20:30 (75 мин). `server/app/planner/layout.py`. Ш-34, 2026-11-21 |
| Точка начала дня (SSOT §4: в брифе только `has_accommodation`) | Центр города (площадь Республики), пока нет жилья (Ш-35); тогда первого перехода нет. Ш-34 |
| Переход по умолчанию между точками | Вариант `recommended` из Ш-22 (пешком до 15 мин, иначе минимум «время + 1 с за тенге»); для расписания берётся верхняя оценка времени. Ш-34 |
| Нет часов работы в базе | Считаем открытым 09:00–21:00 и помечаем `hours_assumed`. Ш-34 |
| Прогноз неизвестен (Ф11 ещё нет) | Горы — утром первого подходящего дня, места не переносятся из-за дождя. День «дождливый» при доле дождливых часов ≥ 0,5 (порог часа — вероятность осадков ≥ 0,5). Ш-34 |
| Валюта и размер группы в расчёте стоимости (SSOT §4, §16.2) | Тенге, на одного человека (в брифе нет числа путешественников); такси и аренда считаются как на одного. Ш-35 |
| Цены, которых нет в базе (OSM их почти не содержит) | Вход: `NULL` = 0 тенге, считается в `entries_unknown`. Обед/ужин без среднего чека: 3000 тенге (`ASSUMED_MEAL_KZT`), помечается `cost_assumed`, в плане предупреждение `meal_prices_assumed`. Жильё без цены за ночь: хостел 7000, гостевой дом 20000, отель 35000, иная категория 20000 тенге (`ASSUMED_NIGHT_KZT`), `price_assumed`. Нет ни одного жилья в базе: ночи × 7000, предупреждение `no_lodging_found`. `server/app/planner/budget.py`. Ш-35 |
| Ночи и какое жильё вычитается из бюджета (SSOT §5.2) | Ночей = дата отъезда − дата приезда (поездка на один день — 0 ночей, жильё не нужно). Предлагается 3–5 вариантов (по кругу по видам: хостел, отель, гостевой дом; мера «км до центра плана + цена / 10 000 тенге»); в бюджет идёт лучший по этой мере (`recommended`). Ш-35 |
| Транспорт в стоимости плана | Верхняя оценка стоимости (`cost_kzt_max`) выбранного по умолчанию варианта каждого перехода; переход без вариантов (нет маршрутизатора) — 0. Ш-35 |
| Превышение бюджета (§16.3) | Оба варианта строятся сразу и хранятся рядом с планом (`trip_items.variant`), пользователь выбирает `POST /v1/trips/{id}/budget-choice` (`drop_places` / `cheaper` / `keep`). `drop_places`: убираем необязательные платные активности по возрастанию ценности (оценка Ш-33), бесплатные не трогаем, приёмы пищи остаются. `cheaper`: самое дешёвое жильё из вариантов + замена платных необязательных активностей и обедов/ужинов более дешёвыми из того же пула. Обязательные не убираются и не заменяются никогда; если одни они дороже бюджета — `must_haves_exceed_budget`. Ш-35 |
| Одна поездка на чат | `trips.chat_id` уникален; повторный `build_trip` обновляет ту же поездку и увеличивает `version`, строки плана заменяются. Ш-36 |
| Обязательное, не влезшее в свой день | Раскладка повторяется до 3 раз с исключением дня, на котором оно не поместилось; если не поместилось нигде — `must_have_unmet` с причиной `no_time`. Ш-36 |
| Правка маршрута: обязательное место (SSOT §4: явные пожелания гарантированы) | Удалить или заменить обязательную остановку без подтверждения нельзя: 409 `must_have`; с `force: true` (в чате модель ставит его только после явного «да» человека) правка выполняется, пожелание попадает в `must_have_unmet` с причиной `removed_by_user` / `replaced_by_user`. В брифе пожелание остаётся, полная пересборка вернёт его. Ш-38 |
| Правка маршрута: варианты бюджета | Варианты `drop_places` / `cheaper` строились для прежнего плана, после правки они устарели: удаляются, `budget.variants = null`, выбор больше не открыт (`budget-choice` отвечает 409); превышение бюджета остаётся предупреждением. Ш-38 |
| Правка маршрута: что пересчитывается | Только день правки: остановки остаются в прежнем порядке, переходы строятся заново, время идёт подряд с начала дня; остальные дни и весь планировщик не трогаются. Замена: кандидат из категории / по названию / по id, берётся первый, после которого день без потерь; иначе 409 `no_replacement`. Выбранные человеком виды транспорта для неизменных пар «откуда–куда» сохраняются. Ш-38 |
| Выбор вида транспорта для перехода | Меняет `chosen_mode`, стоимость (верхняя оценка варианта) и время перехода, пересчитывает транспорт и итог, `version` растёт; расписание дня НЕ пересобирается, опоздание к следующей остановке отдаётся как `late_by_s`. Ш-37 |
| Сигнал памяти правки (SSOT §8) | Каждое удаление / замена пишет строку в `user_place_signals` (`removed` / `replaced`, место, снимок категории); читает Ш-41. Ш-38 |
| Погода: кэш Open-Meteo | Кэш в БД (`weather_cache`) по координате с округлением до 0,01° (≈1 км), высоте с округлением до 100 м (для гор) и дню; TTL 3 часа; при сбое API до 24 часов отдаётся устаревшее; горизонт 16 дней (дальше и прошлые дни — «неизвестно»). Бесплатный API Open-Meteo только для некоммерческого использования — для продакшена нужен платный план (`OPEN_METEO_API_KEY`), атрибуция CC BY 4.0 в приложении. Ш-39 |
| Погода: применение изменений (SSOT §16.4) # OPEN(SSOT §16.4) | Движок только предлагает (`trip_change_proposals`, сообщение ассистента в чате с `proposal_id`, пуш); план меняется после `POST /v1/proposals/{id}/accept`. Одно ожидающее предложение на поездку (следующее — после ответа; после принятия ставится внешний re-check). Предложение, составленное для прежней версии плана, устаревает: `expired`, accept даёт 409 `proposal_stale`. Ш-40 |
| Погода: «день страдает» | Только для outdoor-остановок типа `activity` (не обед). Часы визита: гроза (WMO 95/96/99) в любом часу; иначе не менее 50 % известных часов с дождём (вероятность >= 0,6), ветром >= 40 км/ч или жарой >= 35 °C. Порядок: гроза, дождь, ветер, жара. Часы без прогноза игнорируются. Порог дождя 0,6 выше планировочных 0,5 намеренно: план, построенный при 0,5, не дёргается от колебаний прогноза. Константы в `app/live/rules.py`. Ш-40 |
| Погода: что предлагается | (а) перенести остановку в конец другого дня поездки (не сегодня, ближайший день первым), если оба дня пересобираются без потерь, у остановки там нет проблемы и число страдающих остановок падает; иначе (б) заменить ближайшей крытой активностью (8 км, не еда, не горы, не outdoor), первой, что вписывается в день. Обязательное место (SSOT §4) только переносится, не заменяется. Если ничего нет, предложения нет (в логе). Применение не пишет сигнал памяти: это не вкус человека. Ш-40 |
| Погода: расписание | `weather.scan` раз в час ставит `weather.recheck` для активных поездок (`status = active`, `end_date >= сегодня`), у которых `weather_checked_at` пуст или старше 2 суток; не чаще одной задачи на поездку в сутки. `weather_checked_at` ставится при сборке (если прогноз был) и после каждой проверки. Прогноз при сборке: `build_trip` берёт его у `app.state.weather_provider`; сбой = план без прогноза. Ш-40 |
| Горы: утреннее сообщение (SSOT §7.2) | `mountain.scan` каждые 15 минут; с 07:00 Алматы и пока первая горная остановка дня ещё впереди — `mountain.notify`: свежий (кэш до 3 ч) прогноз в точке и на высоте места, сообщение ассистента в чат (шаблон RU/EN, не LLM) и пуш. Один раз на поездку и день (`trip_day_notices`). Для гор строже: ветер >= 30 км/ч и мороз <= 0 °C на высоте места. Сообщение только о погоде (лавины, тропы, закрытия не учитываются). Если прогноза нет, задача повторяется с отсрочкой; сообщения «прогноза нет» нет. Ш-40 |
| Пуши | Исходящие в таблице `push_notifications` (пишутся в той же транзакции, что сообщение и предложение), доставка задачей `push.send` вне транзакции; по устройствам пользователя (`devices.user_id`, есть `apns_token`); `delivered_to` исключает повтор после сбоя; токен, отвергнутый APNs (410 / BadDeviceToken), стирается. `POST /v1/devices` без токена доступа привязывает устройство ни к кому (вышедшее устройство не получает чужих пушей). Провайдер по умолчанию `log` (ничего не шлёт); `apns` нужны `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY` (платный аккаунт Apple не заведён: разрыв в ключах). Ш-40 |
| Очередь задач: аренда | Захват задачи отдельной короткой транзакцией: `locked_at` (аренда и токен владельца), `attempts + 1`; аренда 300 с (`WORKER_LEASE_SEC`) не продлевается; истёкшая аренда = задача доступна снова, исчерпавшая попытки гибнет; завершение только владельцем аренды; `payload` стирается при завершении (done / dead). Обработчики с внешними вызовами (`external=True`) не держат транзакцию, доставка at-least-once, они идемпотентны. Ш-06 (правки) |

### Соглашение о комментариях в коде

Каждое место, где реализовано допущение по открытому вопросу, помечается комментарием
`# OPEN(SSOT §16.N)` (N — номер вопроса), например `# OPEN(SSOT §16.4)`. В Swift и SQL —
тем же текстом с синтаксисом комментария языка: `// OPEN(SSOT §16.4)`, `-- OPEN(SSOT §16.4)`.
Так все допущения находятся одним поиском `OPEN(SSOT §16.` по репозиторию. Когда владелец решает вопрос: сначала правится `JOL_SSOT.md`
(с записью в журнале §17), затем код, и комментарий убирается.

## Последствия

- Разработка не блокируется открытыми вопросами, а заготовки легко заменить.
- Есть риск, что решение владельца будет отличаться; цена — переделка локальной заготовки.
- Шаги плана, упирающиеся в открытый вопрос, могут получать статус `[!]` (`TECH_PLAN.md §0` п.3).
- Пока ADR в статусе «предложено», строки таблицы обновляются при закрытии вопроса. После
  принятия ADR — по правилам `README.md`: изменение оформляется новым ADR «заменяет 0003».
