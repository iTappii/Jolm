# Ревью Ш-38 — правки маршрута

Удаление и замена остановки (REST и через чат), запись сигнала памяти для Ш-41. Пересчитывается
**один день**: порядок остановок сохраняется, переходы строятся заново, время идёт подряд с
начала дня. Планировщик целиком не запускается.

## Что сделано

- **Миграция `db/migrations/0012_user_place_signals.sql`:** `user_place_signals(id, user_id,
  place_id, category_slug, signal 'removed'|'replaced', trip_id, created_at)`. `user_id` →
  `users ON DELETE CASCADE`; `place_id` → `places` **без каскада**; `trip_id` →
  `trips ON DELETE SET NULL`. `category_slug` — снимок категории на момент правки.
  Правило 8: `merge_place` (`data/osm/merge.py`) переносит сигналы на выжившее место; тест
  `test_merge_moves_user_place_signals_to_the_survivor`. `AUTH_TABLES` в `conftest.py`
  дополнен; тест удаления аккаунта (`test_account_deletion.py`) проверяет, что сигналы
  пользователя удаляются, чужие остаются.
- **Движок** `server/app/trips/edit.py`; `planner/layout.py::retime_day` (повторное время одного
  дня), `planner/travel.py::PreferredLegs` (сохраняет выбранные человеком виды транспорта для
  неизменных пар), `planner/build.py::leg_tools` (общий с `build_plan`), `trips/store.py::replace_day`
  (остановки, оставшиеся в дне, **сохраняют `item.id`**; переходы дня получают новые id).
- Всё выполняется в транзакции клиента с `SELECT ... FOR UPDATE` строки поездки; роутер
  (Valhalla, локально) вызывается внутри транзакции — короткая блокировка, зато нет гонок версии.
- Пересчитывается бюджет по строкам плана (те же правила, что `planner.budget.plan_costs`):
  входы, обеды/ужины, транспорт (выбранные варианты), жильё как было. Обновляются `budget`,
  `total_cost_kzt`, предупреждения `over_budget` / `must_haves_exceed_budget` /
  `meal_prices_assumed`, `must_have_cost_kzt`. `version` + 1, `updated_at`.
- **Решения** (все в ADR 0003):
  1. Обязательное место: без `force` — 409 `must_have` (текст на RU/EN); с `force: true` правка
     выполняется, в `must_have_unmet` добавляется `reason: removed_by_user` / `replaced_by_user`.
     В брифе пожелание остаётся — полная пересборка вернёт его.
  2. Варианты бюджета после правки удаляются (`budget.variants = null`), `budget-choice` → 409.
  3. Выбор транспорта сохраняется при пересчёте дня для тех же пар «откуда–куда».
  4. Остановка, которая после пересчёта не помещается (часы работы, конец дня), выбывает и
     возвращается в `dropped` (обязательная — ещё и в `must_have_unmet` с `no_time`).
- **Промпт `trip_brief.{en,ru}.v4`:** как менять готовый план (`get_trip_plan` → правка, не
  пересборка), подтверждение для must-have перед `force`.

## REST

### `POST /v1/trips/{id}/items/{item_id}/remove`  тело необязательно: `{"force": false}`

```json
{"trip_id": "<uuid>", "version": 2, "action": "remove", "changed_days": ["2026-12-05"],
 "budget": {"status": "ok", "total_kzt": 118000, "remaining_kzt": 782000,
            "shortfall_kzt": 0, "breakdown": {"lodging_kzt", "entries_kzt", "meals_kzt",
                                             "transport_kzt", "events_kzt"}},
 "removed": {"item_id": "<uuid>",
             "place": {"id", "name", "name_lang", "category", "lat", "lon"}},
 "dropped": [{"place": {"id", "name"}, "reason": "no_time", "must_have": false}]}
```

### `POST /v1/trips/{id}/items/{item_id}/replace`  `{"place_id"? | "category"? | "query"?, "force"?}`

Ровно одно из `place_id`, `category` (slug), `query` (часть названия, ≥ 2 символов), иначе 422.

```json
{"trip_id", "version", "action": "replace", "changed_days": [...], "budget": {...как выше},
 "replaced": {"item_id": "<старый>", "place": {...}},
 "replacement": {"item_id": "<новый>",
                 "place": {"id", "name", "category", "lat", "lon"}},
 "dropped": []}
```

- Кандидаты: активные места не-жильё, не входящие уже в поездку. По категории — ближе к
  заменяемому месту и популярнее; по названию — порядок поиска (как у обязательных пожеланий).
  Пробуются до 5; берётся первый, после которого день **без потерь** (никто не выбыл).
  Для обеда/ужина годится только еда (не кофе/пекарня/бар). Нет подходящего — 409
  `no_replacement`.
- Остановка заменяется **на той же позиции** того же дня; вид (`kind`/`meal`) сохраняется,
  `must_have` у новой — `false`.
- Ошибки: 404 (чужая/несуществующая поездка или остановка, повторное удаление), 409
  `must_have`, 409 `no_replacement`, 422.
- Читать результат: `GET /v1/trips/{id}` (id остановок оставшихся мест прежние, у переходов
  дня новые; новая остановка при замене — `replacement.item_id`).

## Чат

Инструменты (`server/app/chat/edit_tools.py`, подключены в `chat/api.py`):

- `get_trip_plan {}` → `{ok, trip_id, version, days: [{date, stops: [{item_id, time, name, kind,
  category, cost_kzt, meal?, must_have?}]}], budget: {budget_kzt, status, total_kzt}}`. Нужен,
  потому что история чата не хранит результаты инструментов: в следующем сообщении модель не
  знает `item_id`.
- `remove_trip_item {item_id, force?}`, `replace_trip_item {item_id, place_id? | category? |
  query?, force?}` → результат REST + `days` изменённых дней + `warnings` (коды). Ошибка (как
  `ok: false`): `must_have` (с подсказкой спросить подтверждение), `no_replacement`,
  `not_found`; нет поездки в чате — «сначала `build_trip`».
- Результат `build_trip` теперь тоже содержит `item_id` каждой остановки (берутся из БД после
  записи).

**SSE-событие после каждой удачной правки (точная форма):**

```
event: trip_updated
data: {"trip_id": "<uuid>", "version": 3, "action": "remove" | "replace",
       "changed_days": ["2026-12-05"],
       "budget": {"status": "ok" | "over", "total_kzt": 118000, "remaining_kzt": 782000}}
```

Клиент по событию перечитывает `GET /v1/trips/{id}` (изменённые дни). `route_ready` по-прежнему
только после `build_trip`.

## Проверки

`tests/test_trip_edits.py`, 14 тестов: удаление (версия, только нужный день изменился — остальные
дни идентичны, id оставшихся остановок прежние, нет пересечений, переходы по соседним
остановкам, сумма = строки плана, сигнал записан); повтор и чужая остановка — 404; must-have
(409 с RU-текстом, `force`, `must_have_unmet`); удаление обеда и опустошение дня; выбор транспорта
переживает правку дня; варианты бюджета удаляются; замена по категории (та же позиция, новое
место не из поездки, сигнал `replaced`), по id и по названию, отказы (422, жильё, чужая еда,
уже в поездке, must-have); чат: `get_trip_plan` → удаление → замена, два события `trip_updated`,
версии 2 и 3, аудит инструментов; подтверждение must-have в чате; ошибки без поездки и с
плохим id; `build_trip` отдаёт `item_id`. Плюс тест слияния мест и дополненный тест удаления
аккаунта. `make ci`: 544 прошли, 1 пропущен, линтеры чистые.

## Не сделано / не проверено

- Порядок остановок не оптимизируется заново (2-opt) после правки — только пересчёт времени.
  Удаление первой остановки сдвигает день к его началу, а обед ждёт своего окна.
- Замена пробует до 5 кандидатов; хороший, но далёкий вариант может быть пропущен.
- `warnings.hours_assumed` (число мест без часов) после правки не пересчитывается.
- На реальном Valhalla правки не прогонялись (только `FakeRouter`, как сквозные тесты Ш-36).
- Ш-41 (использование сигналов в скоринге) не начат; таблица готова.
- Параллельные правки одной поездки сериализуются блокировкой; отдельной проверки `version` в
  запросе (If-Match) нет.
- Правка не меняет бриф: «ещё один музей» в чате — это либо замена, либо `update_trip_brief` +
  `build_trip`.

## Ревью координатора (2026-11-21)

Миграция `0012_user_place_signals` прочитана: `user_id` с каскадом, `place_id` без каскада,
перенос в `merge_place` с тестом (правило 8), удаление аккаунта удаляет сигналы. Правка идёт под
`FOR UPDATE` строки поездки. Обязательное место удаляется только с `force` и попадает в
`must_have_unmet` с причиной — соответствует SSOT §4. Замечания:

1. **Низко.** Пересчёт дня (маршрутизатор) выполняется внутри транзакции с блокировкой поездки —
   при медленном Valhalla блокировка держится долго. Вынести внешние вызовы до транзакции,
   вместе с доработкой воркера (Ш-40).
2. **Низко.** После правки порядок внутри дня не переоптимизируется и `hours_assumed` не
   пересчитывается.

## Исправления (2026-11-21)

Замечание координатора №1 (маршрутизатор под блокировкой поездки) закрыто: правки работают по
схеме «рассчитать, затем применить».

- `trips/edit.py`: `remove_item`, `replace_item`, `move_item` и `set_leg_mode` сначала читают
  поездку БЕЗ блокировки и считают всё, что требует маршрутизатора (пересчёт дня, кандидаты
  замены, варианты пути). Только после этого берётся `FOR UPDATE` строки поездки, `version`
  сравнивается с прочитанной, и под блокировкой выполняются одни записи. Версия растёт при любой
  правке плана, поэтому совпадение версии гарантирует, что рассчитанное по-прежнему верно.
- Если поездка изменилась между фазами, запись не делается и поднимается 409 `trip_changed`. API
  (`trips/api.py::_edit`) один раз повторяет запрос целиком в новой транзакции (блокировка
  снимается откатом); при втором 409 клиент получает `409 {"error": {"code": "trip_changed"}}`.
  Новые необязательные параметры функций: `expected_version` (для принятия предложения).
- `live/store.py::proposal_for_update` теперь блокирует только строку предложения, а не поездку
  (`live/proposals.py::accept` читает поездку без блокировки; рассчитанное изменение применяется
  с `expected_version = trip_version` предложения). Путь «предложение устарело» не изменился:
  409 `proposal_stale`.
- Не тронуто: воркер проверки погоды (`live/jobs.py`, `engine.find_proposal`) по-прежнему считает
  под блокировкой строки поездки — отдельная доработка.
- Тесты (`tests/test_trips_followups.py`): порядок вызовов (все вызовы маршрутизатора раньше
  единственной блокировки), поездка изменилась во время расчёта один раз (повтор, одна
  применённая правка), изменяется всё время (409 `trip_changed`, версия и данные не изменились,
  сигнал памяти не записан). В тестах общая транзакция, поэтому реальную конкуренцию строк БД
  они не воспроизводят: гонка имитируется изменением версии из маршрутизатора.
