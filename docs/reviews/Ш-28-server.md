# Ревью Ш-28 (серверная часть) — удаление аккаунта

- Дата — 2026-11-21.
- Статус — серверная часть готова. iOS-часть Ш-28 (экраны входа, гейт, UI-тест) сюда не входит.
  Отзыв токена Apple проверен только на моках: реальных учётных данных Apple нет.

## Что сделано

- `DELETE /v1/me` (Bearer): в одной транзакции проверяет сессию и удаляет аккаунт, ответ 204.
  Логика в `app/auth/accounts.py`.
- Удаление **жёсткое**: строка `users` удаляется, каскадом уходят `auth_identities`, `sessions`,
  `devices`. Старые токены перестают работать сразу: access проверяется по живой сессии в БД
  (401), refresh не находит сессию (401).
- Почему раньше был 401 при повторной регистрации (Ш-24 №2, Ш-26 №3): `users.deleted_at`
  оставлял `auth_identities` с тем же `(provider, subject)`, а `sign_in` отвечал 401 для личности
  с удалённым пользователем. Теперь личность удаляется вместе с пользователем, и тот же адрес,
  номер или Apple ID создаёт нового пользователя. Колонка `deleted_at` и проверки в
  `sessions.py` оставлены как защита, но нигде не выставляются.
- `otp_codes` не связана с пользователем (только HMAC адреса), поэтому при удалении для почты и
  телефона строки удаляются по хешу адреса.
- Гонка вход/удаление: удаление берёт ту же advisory-блокировку личности (`lock_identity`), что и
  `sign_in`.
- Миграция `0008_account_deletion.sql`: `auth_identities.provider_refresh_token` и внешний ключ
  `place_photos.author_user_id → users ON DELETE SET NULL` (фото, присланные пользователем,
  остаются у места без автора). Правило 8 плана: таблиц пользователя со ссылкой на `places` без
  `ON DELETE CASCADE` нет; `place_photos` уже обрабатывается в `merge_place`, он не менялся.
- Фикстура `committed_auth_db_url` теперь чистит и `place_photos` (иначе `TRUNCATE users` не
  выполняется из-за нового внешнего ключа).

### Отзыв токена Apple

- `app/auth/apple_grants.py`: интерфейс `AppleGrants` (`exchange_code`, `revoke`), адаптеры:
  `HttpAppleGrants` (ES256 client secret на 5 минут; `/auth/token`, `/auth/revoke`),
  `StubAppleGrants` (dev/test, только лог), `MissingCredentialsGrants` (prod без ключей:
  `revoke` падает, задача остаётся видимой в `jobs`). Выбор по настройкам `APPLE_TEAM_ID`,
  `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (в `.env.example`).
- `POST /v1/auth/apple` принимает необязательное `authorization_code`. Если ключи настроены,
  код обменивается на refresh-токен Apple, он шифруется (Fernet, ключ из `AUTH_SECRET`) и
  сохраняется в `provider_refresh_token`. Ошибка обмена или чужой `sub` не ломают вход.
- Удаление аккаунта кладёт задачу `apple.revoke` в очередь `jobs` в той же транзакции
  (`dedupe_key` по `user_id`); обработчик в `worker.py` расшифровывает токен и вызывает Apple.
  Сбой — обычные ретраи воркера с бэкоффом; на удаление это не влияет. Ответ 400
  `invalid_grant` (уже отозван) считается успехом.
- **Пробел в учётных данных:** нет ни ключа Sign in with Apple, ни Team ID. Пока их нет,
  токен не сохраняется, при удалении пишется предупреждение `apple token not revoked`, а Apple
  о удалении не узнаёт. Нужно: создать ключ в Apple Developer, заполнить три переменные,
  и **iOS должен присылать `authorization_code`** (`ASAuthorizationAppleIDCredential.authorizationCode`).

## Замечания

1. **Реальный вызов Apple не проверялся** (средняя): формат формы и ответов взят из
   документации; нужен прогон с настоящим ключом и тестовым Apple ID.
2. **iOS не присылает `authorization_code`** (средняя): без него токен не сохраняется, отзыв
   невозможен. Передать код в `AppleSignInView`/`APIClient` в iOS-части Ш-28.
3. **Ключ шифрования выводится из `AUTH_SECRET`** (низкая): смена секрета делает сохранённые
   токены нечитаемыми, отзыв упадёт с логом. Отдельный ключ — в Ш-51.
4. **Лимит отправки кодов обнуляется удалением** (низкая): строки `otp_codes` адреса
   удаляются, поэтому лимит «3 кода за 10 минут» по этому адресу можно сбросить циклом
   вход-удаление; лимит по IP остаётся. Альтернатива — удалять только строки старше окна.
5. **Данные, которые ещё появятся** (напоминание): чаты, бриф, память, бонусы (Ш-31+) должны
   ссылаться на `users` с `ON DELETE CASCADE` и попадать в тест удаления.
6. Обмен кода идёт до проверки одноразовости challenge, повторённый токен лишний раз вызывает
   Apple (низкая).

## Ревью координатора (2026-11-21)

Код прочитан, `make ci` перезапущен: Ruff чисто, 327 тестов прошли, 1 пропущен. Каскад
удаления, блокировка identity общая с `sign_in`, FK `place_photos` без каскада на `places`
(правило 8) — в порядке. Замечания:

1. **Средне.** Ключ Fernet выводится из `AUTH_SECRET`: смена секрета сделает сохранённые
   токены Apple нерасшифровываемыми, и отозвать их будет нельзя. До продакшена — отдельный
   ключ шифрования с поддержкой ротации (`MultiFernet`).
2. **Низко.** `_exchange_code` ходит в Apple до проверки одноразового nonce: повторно
   присланный токен вызовет внешний запрос до отказа 401. Коды Apple одноразовые, поэтому
   вреда мало; перенести обмен после проверки challenge при работе над Ш-28 iOS.
3. **Низко.** Зашифрованный токен остаётся в `jobs.payload` после выполнения задачи до
   очистки, а у упавших задач — бессрочно. Очищать payload при завершении — вместе с
   доработкой воркера до Ш-40.
4. **Низко.** Удаление аккаунта сбрасывает лимит отправок кода на этот адрес (лимит по IP
   остаётся).
5. iOS должен передавать `authorization_code` из `ASAuthorizationAppleIDCredential` — в iOS-части Ш-28.

## Исправления (2026-11-21, Ш-51)

Замечание координатора №1 закрыто: токены Apple шифруются `MultiFernet` с ключами из
`TOKEN_ENCRYPTION_KEYS` (первый шифрует, все расшифровывают), ключ больше не выводится из
`AUTH_SECRET` (в dev/test без явных ключей остаётся прежний выведенный ключ, чтобы старые базы
читались). Ротация: новый ключ первым, `python -m app.auth.keys rotate`, затем убрать старый.
Миграция с прежнего выведенного ключа: `LEGACY_TOKEN_SECRET` (только расшифровка), порядок в
`docs/deploy.md`. Тесты: `server/tests/test_keys.py` (ротация, потеря старого ключа, миграция).
Замечание №3 (payload задачи) к этому моменту уже было закрыто в воркере (payload стирается при
завершении).
