# Ш-64 (сервер): чат не ждёт карту

Ветка `sh-64-server`. SSOT §11.1 («Чат не ждёт карту»), TECH_PLAN Ш-64. Половина iOS — отдельно.

## Что изменилось

- `update_trip_brief` сохраняет бриф, сразу отдаёт `brief_updated` и, если изменились `must_haves`,
  **не ждёт** `live_route.sync`: ставит фоновый проход (`chat/live_bg.py`) и шлёт в поток сообщения
  `live_route_status {"state":"building"}`. В результат инструмента для модели добавлено
  `"live_route": "building"`; второй раунд модели стартует сразу.
- Фоновый проход: читает **последние** `must_haves` из сохранённого брифа в момент старта, работает
  под `chat_lock` (сериализация между воркерами и с `choose`), схлопывает запросы: пока идёт проход,
  новые запросы лишь помечают чат «грязным», после прохода выполняется **ровно один** дополнительный
  проход (побеждает последний). Задачи держатся сильными ссылками, ошибки логируются, при остановке
  приложения (lifespan) отменяются; блокировку хода (`turn_lease`) проход не держит.
- Конец прохода объявляется через Postgres `NOTIFY chat_events` с маленькой полезной нагрузкой
  `{"chat": "<uuid>", "kind": "building"|"live_route"|"failed"}` (`chat/events_bus.py`). Маршрут в
  нагрузку не кладётся: подписчик перечитывает его из БД.
- Новый `GET /v1/chats/{id}/events` (SSE, bearer, только владелец чата, как `GET /chats/{id}`):
  сразу снимок `live_route` + `live_route_status` (`building`, если проход этого чата идёт на этом
  воркере, иначе `ready`), затем на каждое объявление — `live_route` + `live_route_status`
  (`building` / `failed` — только статус). Комментарий `: keepalive` каждые 15 с, поток закрывается
  через 10 минут. На процесс одно общее LISTEN-соединение (переподключение с нарастающей паузой,
  после переподключения подписчикам уходит «перечитай всё»).
- Если проход закончился до `done` сообщения, перед `done` в потоке сообщения идут `map_places`
  (старые клиенты), `live_route`, `live_route_status ready` (или `failed`); никогда не ждём.
- `POST /chats/{id}/live-route/choose` по-прежнему синхронный, но после успеха делает NOTIFY.
- `_fill_legs`: недостающие рёбра считаются параллельно (`asyncio.gather`, семафор 4,
  `LEG_CONCURRENCY`); тарифы и транспортная сеть читаются один раз на проход (`leg_context`), потому
  что на соединении под `chat_lock` параллельные транзакции невозможны. Результаты и кэш прежние.
- `build_trip` ждёт окончания прохода этого чата (`TurnLive.wait_idle`), иначе генератор взял бы
  устаревшие остановки (`chosen_places`).
- Замеры: одна структурированная строка на ход `chat turn timing` (`first_text_ms`,
  `llm_rounds_ms`, `tools_ms` по именам инструментов, `total_ms`, `error`), строки
  `live route pass` (`sync_ms`), `live route legs` (`legs`, `legs_ms`), `live route runner`
  (`total_ms`, `passes`). Ни текста пользователя, ни id.
- Промпт `trip_brief` v7 (ru, en): карта строится в фоне, не ждать и не называть расстояния/время,
  которых модель не знает. Старые версии не тронуты.
- Гостевой чат (`chat/guest.py`): живого маршрута там нет (нет брифа, ничего не пишется в БД), менять
  нечего.

## Контракт для iOS

Сообщение (`POST /chats/{id}/messages`), новое: `live_route_status {"state":"building"}` сразу
после `brief_updated`, когда изменились пожелания. Перед `done` возможны `map_places`, `live_route`,
`live_route_status ready|failed` (только если проход уже закончился; ждать их нельзя).

События чата (`GET /chats/{id}/events`): `live_route` `{"stops":[...],"legs":[...]}` (пусто:
`{"stops":[],"legs":[]}`) и `live_route_status` `{"state":"building"|"ready"|"failed"}`. Порядок на
подключении: `live_route`, `live_route_status`. Все события идемпотентны (маршрут всегда целиком).
Клиент переподключается при разрыве и по закрытию потока (~10 мин).

## Тесты

Полный прогон сервера: 989 пройдено, 1 пропущен (реальный Valhalla), ruff check и ruff format чистые.
Новый файл `tests/test_chat_background.py` (16 тестов): текст и `done` приходят при заблокированном
маршрутизаторе, `building` до текста, маршрут сохраняется и NOTIFY доходит, ответ модели содержит
`live_route: building`, проход, закончившийся до `done`, попадает в поток сообщения, гонка трёх
сообщений подряд (ровно два прохода, итог по последнему брифу, проход читает свежий бриф), сбой
прохода (`failed`, маршрут не тронут, дальше работает), отмена при остановке, `choose` шлёт NOTIFY,
эндпоинт событий (401, чужой/неизвестный чат 404, снимок, обновление после NOTIFY, keepalive, статус
`building` при идущем проходе, чужие чаты не просачиваются, одно LISTEN-соединение на несколько
клиентов), параллельные рёбра дают те же рёбра и ограничены 4, известные рёбра не пересчитываются.
Существующие тесты перенесены на новый поток (`tests/test_live_route.py`: `settle` ждёт проход;
`TransactionalDatabase` в `conftest.py` сериализует транзакции задач на одном соединении).

## Было / стало

Стенд: поддельная LLM (раунд 1 — `update_trip_brief` с 3 пожеланиями, раунд 2 — текст),
маршрутизатор с задержкой 300 мс на запрос, 3 остановки (2 ребра), настоящий HTTP через uvicorn и
пул Postgres, замер на клиенте от отправки до события.

| | до (HEAD) | после |
|---|---|---|
| до первого `text_delta` | 795 мс | ~110 мс |
| до `done` | 805 мс | ~120 мс |
| маршрут готов (в фоне) | входит в ход | ~380 мс после инструмента |

Фон быстрее прежнего расчёта вдвое (два ребра параллельно, а не друг за другом).

## Открытые риски

- «building» в снимке знает только воркер, где идёт проход; подписчик на другом воркере сначала
  увидит `ready`, а затем `building`/`live_route` по NOTIFY. Вариант на потом: смотреть
  `pg_locks` по advisory-замку чата.
- NOTIFY, потерянный при обрыве LISTEN-соединения, компенсируется «перечитай всё» после
  переподключения; пока соединение лежит, клиент видит изменения только при своём переподключении.
- `map_places` для новых пожеланий в потоке событий не передаётся (только в потоке сообщения, если
  проход успел): старые клиенты рисуют остановки по `live_route`.
- Остановка сервера отменяет идущий проход: маршрут остаётся прежним, следующее изменение брифа
  запустит проход снова (проход «сам» после рестарта не возобновляется).
- Тестовая БД по защите в `conftest.py` должна называться `*_test`; `TEST_DATABASE_URL` в
  `.env` воркри-дерева исправлена на `jol_sh64_test` (файл вне git).
