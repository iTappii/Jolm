# Ревью Ш-57 (сервер): регионы

## Что сделано

1. **Миграция `db/migrations/0029_regions.sql`.** Таблица `regions`: `id` (slug), названия RU/EN,
   `boundary geometry(Polygon, 4326)` (GiST-индекс), `timezone`, `currency`, `languages text[]`,
   центр (`centre_lat`, `centre_lon`), `camera_zoom`, `is_default` (частичный уникальный индекс:
   регион по умолчанию ровно один). Первая строка — `almaty`: граница — прежний прямоугольник
   `ALMATY_BBOX` (76.70, 42.95, 77.30, 43.45), `Asia/Almaty`, `KZT`, `{ru,en}`, центр
   43.2389 / 76.9455 (прежний `ALMATY_CENTRE`), зум 11 (как `AlmatyCamera.zoom` в iOS).
   Реального полигона города в данных нет, поэтому граница — прямоугольник; настоящие полигоны
   придут с Ш-58 и поменяют только это поле.
2. **Модуль `server/app/regions/`**: `model.py` (`Region`: `tz`, `name(locale)`, `contains`,
   `to_json`), `service.py` (`load_regions`, `refresh` — кеш в процессе, `default_region()`,
   `get_region`, `all_regions`, `region_for_point(conn, lat, lon)` — по настоящей границе через
   `ST_Covers`, при нескольких регионах — наименьший по площади), `seed.py` (встроенная копия
   Алматы, пока кеш не загружен — юнит-тесты без БД; тест сверяет её со строкой БД),
   `api.py`. Кеш заполняется при старте API (`lifespan`) и воркера; пустая таблица оставляет seed.
3. **Константы ушли в регион.** Удалены `planner/area.py`, `ALMATY_TZ` (routing/service,
   places/service), `ALMATY_TZ_OFFSET`, `CITY` (trips/read), `AlmatyPoint` (теперь `RoutePoint`;
   проверка «точка в регионе» — в `routing/api.py`). Везде вместо них `default_region().bbox /
   .centre / .tz / .timezone / .name(locale)`: планировщик (build, candidates, events, layout,
   outside), чат (tools, brief), живой маршрут (clock, engine, jobs), погода (Open-Meteo
   `timezone`), аналитика, админка, события, crowd, транзит, бронирования (`BookingLimits.timezone`),
   чтение поездок (`timezone`, заголовок поездки с городом региона), геокодер. `'Asia/Almaty'` в SQL
   (events/service, crowd/service, admin/sql) заменён параметром `%(tz)s`.
   `today_almaty()` переименован в `today_in_region()`. `TripLayout.start_point` — `default_factory`.
4. **Промпты** (версионируются, старые файлы не тронуты): `trip_brief.{ru,en}.v6.md` и
   `guest.{ru,en}.v4.md`; город — `{{region}}`, валюта — `{{currency}}`, подставляет
   `Prompt.render(today, region)` (по умолчанию — регион по умолчанию, название на языке
   промпта). Тест `test_prompts` обновлён под новые версии (проверка слов «тенге» теперь на
   отрисованном тексте, ищет «KZT»).
5. **API `GET /v1/regions`** — публичный, без авторизации, читает таблицу напрямую. Форма — по
   зафиксированному контракту. Числа: `centre` = `{43.2389, 76.9455}` (фактическое значение
   `ALMATY_CENTRE`; в примере контракта было `76.8897`, но это не значение из кода), `bbox` =
   `[76.7, 42.95, 77.3, 43.45]`, `camera.zoom` = 11.0.
6. **Проверка в CI** — `server/tests/test_regions.py::test_no_city_constants_in_server_code`:
   грепает `server/app` (`.py/.html/.sql/.js/.json`) на `ALMATY_`, `Asia/Almaty`, слово `Almaty`;
   разрешены только `regions/seed.py` и `planner/outside.py`. Отдельный тест требует, чтобы
   последние версии промптов не содержали «Almaty»/«Алматы».

## Изменения поведения (честно)

- **Границы точек.** Раньше `POST /v1/directions` принимал точки в 43.0–43.45 / 76.70–77.20,
  `GET /v1/geocode/reverse` — в 43.00–43.45 / 76.70–77.20, админка событий — в `ALMATY_BBOX`.
  Теперь везде граница региона 42.95–43.45 / 76.70–77.30 (чуть шире у directions и geocode).
  Тест `test_directions_rejects_invalid_input` подправлен: точки вне региона (42.9, 77.31).
- Сообщения об ошибке вне зоны: «The point is outside the region», админка — «Точка вне региона (Алматы)».
- Описания инструментов чата (`search_places`, `search_events`, `OUTSIDE_NOTE`, `build_trip`)
  теперь говорят «регион» вместо «Almaty» (текст инструментов не версионируется).

## Оставшиеся исключения (упоминания Алматы/KZT, которые остались сознательно)

- `regions/seed.py` — встроенная копия региона (сверяется с БД тестом).
- `planner/outside.py` — данные: область «Almaty Region / Алматинская область» в списке известных
  мест вне зоны (это административная область, а не константа города).
- Старые версии промптов (`*.v1–v5`, `guest.*.v1–v3`) — версионированные артефакты, не правятся.
- Миграции и сиды (`db/`, `data/`) — вне `server/app`, не затронуты.
- **KZT / ₸ не трогал**: имена колонок и полей API (`*_kzt`, `budget_kzt`, `cost_kzt_*`,
  `tenge_per_bonus`) — схема данных и контракт с iOS, переименование ломает клиента; допущения цен
  в `planner/budget.py` (`ASSUMED_*_KZT`) и лимиты `MAX_BUDGET_KZT`, `MAX_KZT` — это тенге по
  определению, пока конвертация `OPEN(SSOT §16.2)`; подписи «₸» в админке (`admin/api.py`
  `KZT_SUFFIX`, шаблоны) — русскоязычный служебный интерфейс. В промптах валюта уже берётся из
  региона. Когда появится второй регион с другой валютой, эти места станут следующим шагом
  (цены по регионам — Ш-58+).
- Русские промпты: склонение названия региона не поддержано (для «Алматы» не нужно); для будущих
  регионов потребуется падежная форма в таблице.

## Что не проверено

- Работа с несколькими регионами: все вызовы `default_region()` берут регион по умолчанию, выбор
  региона по точке/поездке (через `region_for_point`) в код планировщика не подключён — это
  Ш-58/61. `region_for_point` проверена только тестами на БД.
- Кеш регионов не обновляется во время работы процесса (только при старте); изменение таблицы
  требует перезапуска.
- Живой запуск сервера на порту 8000 и iOS-клиент под контракт не запускались.
- Контракт: `centre.lon` = 76.9455 вместо 76.8897 из примера — проверить, что iOS не ждёт именно
  второе число.
