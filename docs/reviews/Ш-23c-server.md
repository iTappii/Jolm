# Ревью Ш-23c (сервер) — тап по любой точке карты

Сделана серверная часть: `GET /v1/geocode/reverse?lat=&lon=` (публичный, без токена). Внешние
геокодеры не вызываются (SSOT §13; политика Nominatim запрещает тяжёлое использование из
приложения). iOS-часть шага — отдельно.

## Ответ

Порядок: место из нашей базы в радиусе 30 м → адрес или именованное здание из своих данных OSM
в радиусе 50 м → голая точка. Язык по `Accept-Language` (цепочка ru → en → kk или en → ru → kk).

```json
{"kind":"place","place":{…как в /v1/places: id,name,name_lang,category,kind,lat,lon,is_public,is_partner,popularity},"lat":..,"lon":..,"distance_m":3}
{"kind":"address","address":"улица Панфилова 98","name":null,"lat":43.2579,"lon":76.9450,"distance_m":9}
{"kind":"point","lat":43.30,"lon":77.10}
```

- В `address` `lat/lon` — точка здания (центр), а не место тапа: это надёжная цель для маршрута.
  `address` может быть `null`, если есть только название здания (`name`), и наоборот.
- Вне границ Алматы (bbox импорта мест: 76.70–77.20, 43.00–43.45) — `422 validation_error`.
  Клиент не должен звать метод для тапов за городом.
- Лимит 120 запросов в минуту на адрес клиента (в памяти, как у гостевого чата), `429 rate_limited`
  с `Retry-After`; ответ `Cache-Control: public, max-age=300`. Клиенту стоит не звать метод на
  каждый кадр перетаскивания, а только на тап.
- «В избранное» доступно только для `kind: "place"` (у адреса нет `id`).

## Данные: таблица `osm_addresses`

Миграция `0019_osm_addresses.sql`, импорт `data/osm/import_addresses.py` (`make import-addresses`)
из общего `data/osm/cache/kazakhstan.osm.pbf`. Хранятся узлы и пути с `addr:housenumber` и
именованные здания (`building=*` + имя); путь сводится к центру своих узлов; мультиполигональные
здания пропущены (редки, нужна сборка площадей). Улица: `addr:street` (язык определяется по
буквам, как в импорте транспорта) и `addr:street:ru/en/kk`. Без `place_id`: правило 8 не применимо,
`merge_place` не затрагивается. Таблица — справочник, пользовательских данных нет.

Импорт идемпотентен и атомарен (одна транзакция): COPY во временную таблицу, upsert по
`(osm_type, osm_id)` только изменившихся строк, удаление исчезнувших из выгрузки. Повторный запуск
на dev: `upserted 0, deleted 0`. Места (`places`) не пересоздаются, их id не менялись.

Счётчики на dev (Казахстан целиком, bbox Алматы): прочитано **145 635** строк; с номером дома
145 116, с названием 4 319, с улицей около 140 000 (RU 120 470, KK 19 689, EN 43). Время
~115 с на ядро (весь файл читается заново, как в импорте мест), 32 МБ с индексом (11 МБ индекс).

Примеры (dev, ru): тап у Парка Панфилова (76.9547, 43.2594) → место «Парк имени 28 гвардейцев-
панфиловцев», 25 м; (43.25797, 76.94506) → «улица Панфилова 98», 9 м; (43.2427, 76.96121) →
«переулок Снайперский 11»; (43.24966, 76.94074) → «Kabanbai Batyr St 89» с названием «La Tartine»;
площадь Республики и угол Абая/Достык → `point` (рядом в радиусе 50 м нет здания с улицей и
номером).

## Замечания

1. **Данных об адресах в центре мало.** OSM по Алматы полон на окраинах и неполон в центре: тап по
   площади или перекрёстку часто даёт `point`. Радиус адреса 50 м — компромисс: центр большого
   здания может быть дальше тапа. Для точного «внутри здания» нужны контуры (PostGIS-полигоны), не
   делалось.
2. Улицы с номером без улицы (5 154 строки, `addr:place` и т. п.) в ответ не попадают.
3. Лимит в памяти одного процесса (как у гостевого чата, там же TODO про несколько процессов).
4. Данные ODbL: в приложении нужна пометка © OpenStreetMap (уже есть для карты).
