# Ревью Ш-35 — бюджет и жильё (SSOT §5.2)

Модуль `server/app/planner/budget.py` (чистая логика, без БД), SQL жилья в
`planner/sql.py`, хранение и выбор — `app/trips/` (миграция `0011_trips.sql`, см. ревью Ш-36).

## Что сделано

- **Стоимость плана** = жильё + входы + средние чеки + транспорт + мероприятия (пока 0, Ф16).
  Транспорт — верхняя оценка (`cost_kzt_max`) выбранного по умолчанию варианта каждого
  перехода. Всё в целых тенге на одного человека (в брифе нет числа путешественников).
- **Жильё.** `has_accommodation = true` — не считается. Иначе 3–5 вариантов из базы
  (категории hostel / hotel / guest_house): по кругу по видам, мера «км до центра плана +
  цена/10 000 тенге»; лучший по мере — `recommended`, его стоимость (ночи × цена за ночь,
  ночи = выезд − приезд) вычитается из бюджета. Поездка на один день — 0 ночей. Бронирование —
  Ф16, здесь только варианты.
- **Нет цен в базе** (в OSM их почти нет): вход `NULL` = 0 (считается `entries_unknown`), обед
  без чека = 3000, жильё без цены — по категории (хостел 7000, гостевой дом 20000, отель
  35000). Всё помечено (`cost_assumed`, `price_assumed`) и вынесено в предупреждения. Нет ни
  одного жилья — ночи × 7000 и `no_lodging_found`. Допущения — в ADR 0003.
- **Превышение бюджета (§16.3, по умолчанию из TECH_PLAN §2: показываем оба, выбирает
  пользователь).** Оба варианта строятся сразу как настоящие раскладки (переходы, время и часы
  работы корректны), стоимость считается по новой раскладке, а не оценивается:
  - `drop_places` — убираем необязательные платные активности, начиная с наименее ценных (оценка
    Ш-33); бесплатные не трогаем (экономии нет), приёмы пищи остаются;
  - `cheaper` — самое дешёвое жильё из вариантов + замена платных необязательных активностей и
    обедов/ужинов более дешёвыми из того же пула (предпочитается та же группа, лучшая оценка).
  - До 6 пересборок раскладки на вариант; результат проверяется по факту.
- **Обязательные никогда не убираются и не заменяются.** Если одни они (входы, чеки, самое
  дешёвое жильё) дороже бюджета — `must_haves_exceed_budget` + предупреждение; варианты
  остаются `feasible: false`, а не делают вид, что уложились.
- **`POST /v1/trips/{id}/budget-choice`** `{"choice": "drop_places"|"cheaper"|"keep"}` ->
  `{trip_id, version, budget}`. Выбранный вариант становится планом (`variant = 'main'`),
  `version` + 1, второй вариант удаляется; `keep` принимает план как есть. 401 без токена, 404
  чужая/отсутствующая поездка, 409 `budget_choice_unavailable` (план укладывается или выбор
  уже сделан), 422 неверный `choice`.

## Проверки

- `tests/test_planner_budget.py`, 12 тестов, без БД: расчёт (все четыре статьи, сверка с
  суммой по остановкам и переходам), цены по умолчанию и счётчики, варианты жилья (3–5, виды,
  ночи × цена, `assumed`, мало/нет жилья, 0 ночей), `drop_places` (убирает только платные
  необязательные, наименее ценные первыми, обязательные и еда на месте), `cheaper` (замены
  строго дешевле, жильё, обеды), обязательные дороже бюджета (не убираются ни в одном варианте,
  `feasible = False`), нижняя граница, детерминизм.
- `tests/test_trips.py` (сквозные с БД): превышение с предупреждением и обоими вариантами рядом
  с планом, выбор каждого варианта (строки варианта становятся основными, остальные удалены,
  суммы совпадают, повторный выбор 409), `keep`, смена жилья на дешёвое, обязательные дороже
  бюджета, доступ (401/404/422), «выбирать нечего» (409).
- `make ci`: 504 прошли, 1 пропущен (было 473 + 1).
- Вручную на реальной базе Алматы с Valhalla (скрипт вне репозитория): план на 4 дня строится за
  ~2 с, варианты жилья считаются.

## Не сделано / не проверено

- **В реальной базе почти нет цен** (OSM): все чеки и цены за ночь — допущения, входы = 0. На
  реальных данных при превышении оба варианта экономят 0 (замена «строго дешевле» не находит
  кандидатов, платных активностей нет); пользователю это видно (`feasible: false`,
  `saves_kzt: 0`), но полезными варианты станут только после наполнения цен.
- Транспорт в варианте `cheaper` не удешевляется (режим по умолчанию остаётся «рекомендованным»
  из Ш-22); дешёвый режим меняет время.
- Жильё не влияет на точку начала дня (Ш-34 «жильё -> первая точка»): адрес жилья неизвестен до
  выбора, а выбор — Ф16. Остаётся центр города.
- Размер группы не учитывается (на одного).
- Мероприятия — 0 до Ф16. Вариант `cheaper` не пересматривает уже выбранные необязательные места
  по ценности, только по цене.
- Допущения (цены по умолчанию, формула жилья, правила вариантов) ждут подтверждения владельца,
  ADR 0003.

## Ревью координатора (2026-11-21)

Обязательные пожелания из вариантов не удаляются (есть тест), случай «обязательные дороже
бюджета» отдаётся честно (`must_haves_exceed_budget`, `feasible: false`). Замечания:

1. **Средне.** В реальной базе почти нет цен — расчёт держится на допущениях (еда 3000 ₸,
   ночь по категории), и варианты экономии на реальных данных почти всегда `feasible: false`.
   Нужно наполнение цен (админка Ш-10, UGC Ф14) — до показа бюджета пользователям.
2. **Низко.** Выбор варианта с `feasible: false` не запрещён — клиент должен показать, что
   вариант всё равно не укладывается в бюджет.
3. Цены по умолчанию и правила вариантов — допущения агента, записаны в ADR 0003, ждут владельца.
