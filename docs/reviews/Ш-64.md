# Ш-64. Чат не ждёт карту — ревью координатора

Решение владельца 2026-11-23 (SSOT §11.1): ответ ИИ и узел графа — сразу, заведения и пути живого
маршрута строятся в фоне и догружаются на карту; следующее сообщение можно писать, не дожидаясь карты.

Половины: `docs/reviews/Ш-64-server.md` (ветка `sh-64-server`), `docs/reviews/Ш-64-ios.md`
(ветка `sh-64-ios`). Обе слиты в `sh-22-24-auth`.

## Ревью координатора

- Сервер: `update_trip_brief` больше не ждёт `live_route.sync`; проход идёт в `chat/live_bg.py`
  (один раннер на чат в процессе, повторные запросы — ровно один лишний проход, читает последние
  пожелания из брифа, `chat_lock` между воркерами, без аренды хода). События — `chat/events_bus.py`:
  одно LISTEN-соединение на процесс, NOTIFY с маленьким payload, повторное чтение из БД. Рёбра
  считаются параллельно (семафор 4). Проверил код раннера и шины — гонок по коду не нашёл.
- iOS: подписка на `GET /v1/chats/{id}/events` для открытого чата, переподключение 1/2/5/10 с,
  индикатор «Строю маршрут…», ввод блокируется только пока печатается текст, равный маршрут —
  без перерисовки и озвучки. Заглушка API и демо-режим показывают фоновую догрузку.
- Отличия от исходного контракта (приняты): `building` в снимке виден только на своём воркере;
  `map_places` нет в потоке событий; `live_route` при успехе шлётся всегда (клиент идемпотентен);
  `build_trip` дожидается фонового прохода, иначе планировщик увидел бы старые остановки.
- Замер (фейковая LLM, роутер 300 мс на запрос, 3 остановки): первый `text_delta` 795 → ~110 мс,
  `done` 805 → ~120 мс; маршрут готов в фоне ~0,4 с после вызова инструмента. На настоящем
  DeepSeek не мерили — ключа пока нет.

## Риски

- NOTIFY, потерянный пока LISTEN-соединение лежит, восстанавливается только повторным чтением после
  переподключения.
- Проход, отменённый остановкой сервера, не возобновляется; следующее изменение брифа запустит его.
- Индикатор живёт в узкой верхней полосе; на самых крупных размерах шрифта ограничен xxxLarge.
