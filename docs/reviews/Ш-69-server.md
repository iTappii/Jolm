# Ш-69 (сервер) — главные места на карте

Дата: 2026-11-24. Статус: сервер готов, ждёт ревью координатора. iOS-часть — отдельно.

## Что сделано
- Миграция `db/migrations/0038_landmarks.sql`: таблица `landmarks(place_id PK -> places ON DELETE CASCADE,
  rank, min_zoom, source, as_of)`. Отдельная таблица, а не колонки в `places`: список крошечный, ведётся
  вручную отдельно от OSM-импорта (он переписывает `places`), у него свои `source` и `as_of`.
- Сид `data/seed/landmarks.sql` (грузится из `load_seed.py`): места находятся по ключу OSM
  (`osm_type`, `osm_id`), ручное место без OSM (Кольсай) — по названию; отсутствующие пропускаются с
  `RAISE WARNING`; идемпотентно (upsert по месту).
- `GET /v1/landmarks` (`server/app/landmarks/api.py`): публичный, без входа, RU/EN по `Accept-Language`
  (как карточка места: нет английского имени — русское), `Cache-Control: public, max-age=3600`, `ETag`
  (sha256 тела) и 304 по `If-None-Match`, `Vary: Accept-Language`. Лимитера нет: у публичных
  `/v1/places*` его тоже нет. Только `status = 'active'`. Регион — самый маленький регион, покрывающий
  точку (как `regions.service.FOR_POINT`). Сортировка: `region`, `rank`.
- Контракт ответа ровно как в задаче: `id, name, category, lat, lon, min_zoom, rank, icon, region`.

## Отклонения и заметки
- Контракт не менялся. Для остальных регионов в базе по одному месту на кластер (Туркестан, Чарын,
  Кольсай — по одному объекту в `country_places.csv`), поэтому «2–4 на город» невозможно; все три лежат в
  регионе `kazakhstan` (отдельных регионов для них нет), ранги 1–3.
- Лимит запросов не добавлялся (см. выше); ответ маленький и кэшируется.
- Сид проверен на dev-базе только чтением: все 11 ключей находятся и активны. В dev-базу ничего не писалось.
