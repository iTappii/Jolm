# Ревью Ш-40 — перепроверка маршрута по погоде, горы, пуши

Сервер: прогноз Open-Meteo (Ш-39) подключён к сборке плана и к периодической перепроверке;
при ухудшении прогноза движок **предлагает** изменение, применяется оно после подтверждения
(TECH_PLAN §2, рабочее допущение SSOT §16.4). Утренние сообщения про горы (SSOT §7.2). Пуши через
`PushProvider`. Воркер доработан до этого (см. «Исправления» в `Ш-01-03-06.md`). iOS не затронут.

## Что сделано

- **Миграция `0014_live_plan.sql`:** `trip_change_proposals` (`user_id`, `trip_id` каскадом;
  `place_id`, `target_place_id` → `places` **без каскада**; `diff` только числа; один `pending` на
  поездку — частичный уникальный индекс), `chat_messages.proposal_id`, `trip_day_notices`
  (идемпотентность горного сообщения), `push_notifications` (исходящие, `delivered_to`, `sent_at`).
  Правило 8: `merge_place` переносит оба поля предложений, тест
  `test_merge_moves_trip_change_proposals_to_the_survivor`; `AUTH_TABLES` дополнен; удаление
  аккаунта проверено (`test_deleting_the_user_removes_…`).
- **Сборка:** `build_trip` берёт прогноз у `app.state.weather_provider` (в `lifespan` создаётся
  `OpenMeteoProvider`), передаёт в `build_plan`, ставит `trips.weather_checked_at`; сбой прогноза =
  план без него и `weather_checked_at = NULL` (поездка сразу «к проверке»).
- **Правила** `app/live/rules.py` (пороги в ADR 0003): гроза в любом часу визита; дождь
  (вероятность >= 0,6), ветер >= 40 км/ч, жара >= 35 °C — не менее 50 % известных часов визита.
  Только outdoor-остановки-активности.
- **Движок** `app/live/engine.py`: одно предложение на проверку. Сначала перенос остановки в
  конец другого дня (не сегодня; оба дня пересобираются без потерь, проблемы нет, страдающих
  остановок меньше), иначе замена ближайшей крытой активностью (`planner/sql.py::INDOOR_NEAR`);
  обязательное место только переносится. Устаревшие (версия плана) и снявшиеся (прогноз
  улучшился) ожидающие предложения закрываются `expired`; живое ожидающее блокирует новые.
  Отклонённая/принятая остановка на тот же день повторно не предлагается.
- **Правка** `trips/edit.py`: `plan_move`/`move_item` (перенос), `first_fit_replacement`
  (вынесено из `replace_item`), `forecast` и `record_signal` в `replace_item` (применение
  погодной замены не пишет сигнал памяти). Прогноз при применении нужен только для `rain_exposed`.
- **Задачи** `app/live/jobs.py`: `weather.scan` (час), `weather.recheck`, `mountain.scan` (15 мин),
  `mountain.notify`, `push.send`. Часы — `app/live/clock.py` (подменяется в тестах), зависимости
  (прогноз, роутер, пуш) — `app/live/deps.py`.
- **Пуши** `app/push/`: `PushProvider`, `LogPushProvider` (по умолчанию, ничего не шлёт),
  `ApnsProvider` (HTTP/2, JWT ES256, токен переиспользуется 40 мин; 410/BadDeviceToken →
  устройство забывается). `httpx[http2]` добавлен в зависимости. Настройки: `PUSH_PROVIDER`,
  `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY`, `APNS_TOPIC`, `APNS_SANDBOX`
  (`.env.example` дополнен).

## Эндпоинты

`GET /v1/trips/{id}/proposals` (Bearer) → `{"items": [...]}`, новые первыми, до 50:

```json
{"id": "<uuid>", "trip_id": "<uuid>", "reason": "weather", "kind": "move_day" | "replace",
 "status": "pending" | "accepted" | "declined" | "expired", "trip_version": 1,
 "day": "2026-12-05", "to_day": "2026-12-06" | null, "item_id": "<uuid>",
 "problem": {"type": "rain|thunderstorm|wind|heat", "hours": [10, 12], "peak": 0.9 | null},
 "place": {"id", "name", "category", "lat", "lon"},
 "target_place": {...} | null,
 "created_at": "...+06:00", "decided_at": null}
```

`pending` для плана другой версии отдаётся как `expired`.

- `POST /v1/proposals/{id}/accept` → результат правки (`trip_id`, `version` + 1, `action`
  `"move"` | `"replace"`, `changed_days` (для переноса два дня), `budget`, `moved` /
  `replaced`+`replacement`) и `"proposal": {"id", "status": "accepted"}`. Ошибки: 404 (чужое /
  нет), 409 `proposal_decided`, 409 `proposal_stale` (статус `expired` сохраняется), 409
  `proposal_not_applicable` / `no_replacement` (не вписывается, остаётся `pending`).
  Id остановки при переносе **меняется** (в `moved.item_id` новый); клиенту перечитать
  `GET /v1/trips/{id}` (версия выросла).
- `POST /v1/proposals/{id}/decline` → `{"id", "status": "declined"}`; 409 `proposal_decided`.
- `POST /v1/devices` `{"install_id": uuid, "apns_token": hex | null, "language": "ru"|"en"}` →
  `{"install_id", "user_linked", "push_enabled"}`. Bearer не обязателен: без него устройство
  «гостевое» и ни к кому не привязано. Клиент вызывает при запуске, после входа и выхода, при
  новом APNs-токене. Токен, переехавший на другой `install_id`, снимается со старой строки.

## Чат и SSE

SSE-событий не добавлено. Сообщение ассистента кладётся в чат поездки как обычная запись
(`role: assistant`, `finish: stop`), чат поднимается наверх списка. В `GET /v1/chats/{id}` у
каждого сообщения новое поле `proposal_id` (uuid | null): у погодного предложения оно заполнено,
под такими сообщениями показывать «Принять / Отклонить». Горные сообщения — просто текст.
Открытый чат сам не обновляется (потока нет): клиент перечитывает чат по пушу/при открытии.
Тексты — шаблоны RU/EN (язык чата), не LLM. Данные пуша: `type` (`weather_proposal` |
`mountain_morning`), `trip_id`, `proposal_id`, `chat_id`.

## Проверки

`tests/test_live_plan.py`, 24 теста (без сети, настоящие пуши невозможны: провайдер `log`/фейк):
пороги правил; сборка с прогнозом и `weather_checked_at`; предложение + сообщение + пуш-задача;
список, принятие (перенос), повторное принятие; замена на крытое при дожде во все дни;
обязательное место не заменяется; устаревшее предложение (после правки) → `expired` + 409,
статус сохранён; отклонение и отсутствие повтора; снятие при улучшении прогноза; чужой доступ;
сбой прогноза (задача падает, не штампуется); расписание (47/49 часов, пусто, закончена,
архив, дедуп в сутки) на фейковых часах; прогон через воркер; горы (до 07:00, после начала, не тот
день, дедуп, свежий прогноз по точке и высоте, RU-предупреждение, сбой прогноза, идемпотентность);
доставка пуша по устройствам, повтор без дублей, стирание мёртвого токена, частичный сбой; запрос
APNs на `MockTransport` (URL, заголовки, JWT ES256, обновление, 410, 503, прод-хост);
`POST /v1/devices`. `make ci`: 575 прошли, 1 пропущен, линтеры чистые.

## Не сделано / не проверено

- **Пуш на настоящем устройстве проверить нельзя:** нет платного аккаунта Apple (ни team id,
  key id, .p8, ни регистрации push-возможности у приложения). Адаптер APNs написан по документации
  и проверен только на моке; реальный обмен с Apple не пробовался.
- Горное сообщение: если прогноза нет, задача повторяется (5 попыток с отсрочкой) и затем
  умирает без сообщения; сообщения «прогноза нет» нет.
- Нет предложения, когда подходящей замены/переноса не нашлось: человек не узнает о плохой
  погоде (только лог). Возможное расширение: информационное сообщение без кнопок.
- Прогноз один на город (центр Алматы) для обычных мест; для гор — по точке и высоте. Свежесть
  «свежего» прогноза в горах — кэш до 3 часов.
- Перенос остановки идёт в конец другого дня; порядок внутри дня не оптимизируется. Правка
  сегодняшнего дня пересобирает его с начала дня (как и обычные правки Ш-38).
- Перепроверка не обновляет `rain_exposed` у остановок без предложения и не поднимает версию.
- Принятие выполняется под блокировкой поездки с вызовом роутера (замечание Ш-38 №1 остаётся).
- Автоматический пуш о предложении уходит на все устройства пользователя на языке чата, а не
  устройства.
- Обязательная для запуска лицензия: платный Open-Meteo (см. Ш-39) — перепроверка увеличивает
  число запросов (один город + горные точки).

## Ревью координатора (2026-11-21)

Миграция `0014_live_plan` прочитана: пользовательские таблицы с каскадом от `users`/`trips`,
`place_id`/`target_place_id` без каскада и с переносом в `merge_place` (правило 8). Аренда задач
воркера: захват отдельной короткой транзакцией, завершение только владельцем аренды, payload
стирается при `done`/`dead`. `make ci` перезапущен — 575 прошли, 1 пропущен. Шаг `[~]`: DoD
требует ручной проверки пуша на устройстве — невозможно без платного аккаунта Apple. Замечания:

1. **Средне.** Сообщение о предложении приходит в чат, но открытый чат сам не обновляется
   (нет SSE вне хода) — iOS должен перечитывать чат по пушу и при открытии; без пушей (нет APNs)
   пользователь узнает о предложении только открыв чат. Учесть в Ш-32.
2. **Низко.** Аренда задачи не продлевается: задача дольше `WORKER_LEASE_SEC` (300 с) может
   выполниться дважды — внешние обработчики должны быть идемпотентны (сейчас так и есть).
3. **Низко.** Ш-38 №1 (маршрутизатор под блокировкой поездки) не сделан — нужен разрыв на
   «рассчитать» и «применить».
