# Jol — технический план (ТЗ на реализацию)

> Пошаговый план, по которому строится приложение. Источник продуктовых решений — только
> `JOL_SSOT.md`; этот файл переводит их в инженерные шаги. Если план и SSOT расходятся — прав SSOT,
> план правится.
>
> Создан: 2026-11-21. Состояние репозитория на эту дату: кода нет, есть только `JOL_SSOT.md`,
> `CLAUDE.md`, логотипы (`logo/`, фирменный цвет `#FF7A00` + чёрный) и `graphify-out/`.

## 0. Правила исполнения

1. **Работаем только по этому плану.** Каждый шаг имеет ID (`Ш-xx`), цель, задачи и критерий
   готовности (DoD). Шаги делаются по порядку внутри фазы; фазы — в порядке, указанном в §7,
   если у шага не указано иное.
2. Перед началом шага — перечитать связанные пункты SSOT (в скобках `SSOT §x`).
3. Статусы шагов: `[ ]` не начат, `[~]` в работе, `[x]` готов (DoD выполнен), `[!]` заблокирован
   (указать чем — обычно открытым вопросом SSOT §16).
4. **Открытые вопросы SSOT не решаем молча.** Если шаг упирается в `[открыто]`, делаем
   расширяемую заготовку с поведением «по умолчанию» из §2 этого плана и помечаем её в коде
   комментарием `# OPEN(SSOT §16.N)`. Окончательное решение — за владельцем, потом сначала SSOT,
   потом код.
5. Жёсткие технические правила (SSOT §14.1):
   - **никакого ORM**; только чистый параметризованный SQL через `psycopg` 3;
   - миграции — `db/migrations/NNNN_описание.sql`, только вперёд, применённые не редактируются;
   - никакой склейки SQL со значениями пользователя (имена таблиц/колонок — только из белого списка).
6. Общий DoD для любого шага с кодом:
   - тесты шага написаны и проходят (`make test`);
   - линтеры чистые (`ruff`, `swiftlint`);
   - `graphify update .` выполнен;
   - если менялось продуктовое решение — обновлён `JOL_SSOT.md` (включая журнал §17);
   - статус шага в этом файле обновлён;
   - написано ревью шага в `docs/reviews/`.
7. Старый проект Jol не используется. Из его подхода берём только «MapLibre + тайлы OSM».
8. Импорт OSM сливает дубли и удаляет лишние строки `places` (`data/osm/merge.py`). Каждая
   новая таблица со ссылкой на место (`place_id`) добавляется в `merge_place` в той же задаче,
   с тестом; FK пользовательских данных на `places` — без `ON DELETE CASCADE`.

## 1. Цель первой версии (v1) и границы

**v1 = iOS-приложение для туриста в Алматы на RU/EN**, в котором:

- гость видит карту, карточки мест, готовые маршруты, строит маршрут до одной точки, говорит
  с ИИ без памяти (SSOT §3.1, §6);
- зарегистрированный пользователь (почта / Apple / SMS) в чате с ИИ собирает поездку, получает
  маршрут на все дни с транспортом между точками, бюджетом и жильём, видит его на полной карте,
  редактирует, скачивает (SSOT §3.2, §4, §5, §7.4, §11);
- план «живой»: перепроверка погоды раз в ~2 дня и утреннее сообщение в день похода в горы
  (SSOT §7.1–7.2);
- ИИ помнит отклонённые места и прошлые поездки (SSOT §8);
- пользователи присылают контент и получают бонусы (SSOT §10).

**Не входит в v1** (SSOT §15): Android/веб, другие города, межгород, языки кроме RU/EN.
Бронирования (SSOT §9) и загруженность (SSOT §7.3) делаются в v1 как каркас — их полноценная
работа зависит от партнёров и выбранного источника данных.

| 6 | Офлайн-карта | Не делаем в v1; скачиваем только данные маршрута |

| 11 | Нет партнёра под обязательное пожелание | Этап 1: все места на карте, проблемы нет. Флаг `must_have_unmet` в маршруте + честное сообщение ИИ |

## 3. Архитектура

```
 iOS (Swift, SwiftUI, MapLibre Native)
   │  HTTPS JSON  +  SSE (стрим чата)  +  APNs (пуши)
   ▼
 API: FastAPI (Python 3.12, uvicorn)
   ├── auth        — OTP почта/SMS, Sign in with Apple, сессии
   ├── places      — места, карточки, поиск, фото, меню, цены
   ├── routing     — маршрут до точки, варианты транспорта, цены
   ├── chat        — диалог с ИИ, извлечение параметров поездки, граф тезисов
   ├── planner     — детерминированный генератор маршрута на поездку
   ├── trips       — маршруты пользователя, правки, скачивание
   ├── live        — погода, горы, предложения изменений
   ├── ugc         — присланный контент, автофильтр, модерация, бонусы
   ├── bookings    — адаптеры партнёров (каркас)
   └── admin       — простая веб-админка (места, события, модерация, готовые маршруты)
   │
   ├── worker (тот же код, отдельный процесс): планировщик задач — погода, горы, пуши,
   │   пересчёт агрегатов загруженности и коэффициентов спроса
   ▼
 PostgreSQL 16 + PostGIS 3   (единственное хранилище состояния)
 Объектное хранилище S3-совместимое — фото
 Valhalla (Docker, данные OSM Казахстана) — пешком / самокат / авто
 Тайлы: PMTiles (Planetiler + OSM Казахстана) на статическом хостинге/CDN
 Внешние: Open-Meteo, провайдер LLM, провайдер SMS, почтовый провайдер, APNs
```

Ключевые архитектурные решения `[предложено]`:

- **ИИ понимает, движок планирует.** LLM извлекает параметры поездки, формулирует тезисы и
  объясняет план. Сам маршрут (выбор мест, раскладка по дням, время, бюджет) строит
  детерминированный `planner` на сервере — иначе нельзя гарантировать «обязательные пожелания
  всегда в плане» (SSOT §2.3) и бюджет.
- **Очередь задач — в самом Postgres** (таблица `jobs` + `SELECT … FOR UPDATE SKIP LOCKED`),
  без Redis/Celery. Меньше движущихся частей.
- **Стрим чата — Server-Sent Events**: события `text_delta`, `graph_node`, `map_places`,
  `brief_updated`, `route_ready`, `done`.
- Все деньги — целые тенге (`bigint`), все времена — `timestamptz`, часовой пояс поездки
  `Asia/Almaty`.

## 6. API (черновик)

Префикс `/v1`. Ответы JSON, ошибки `{"error": {"code", "message"}}`, язык — `Accept-Language`.

| Группа | Эндпоинты |
|---|---|
| auth | `POST /auth/otp/request` (email или phone) · `POST /auth/otp/verify` · `POST /auth/apple` · `POST /auth/refresh` · `POST /auth/logout` · `DELETE /me` (удаление аккаунта) |
| me | `GET /me` · `PATCH /me` (язык, имя) · `GET /me/bonuses` |
| places | `GET /places?bbox=&category=&q=` · `GET /places/{id}` · `GET /categories` · `GET /curated-routes` · `GET /curated-routes/{id}` |
| routing | `POST /directions` `{from, to_place_id, depart_at}` → варианты по видам транспорта |
| chat | `POST /chat/guest` (SSE, без сохранения) · `POST /chats` · `GET /chats` · `GET /chats/{id}` · `POST /chats/{id}/messages` (SSE) |
| trips | `GET /trips` · `GET /trips/{id}` · `POST /trips/{id}/items/{item}/remove` · `POST /trips/{id}/budget-choice` · `GET /trips/{id}/offline` · `GET /trips/{id}/proposals` · `POST /proposals/{id}/accept|decline` |
| ugc | `POST /uploads` (presigned URL) · `POST /submissions` · `GET /me/submissions` |
| crowd | `POST /places/{id}/crowd` · `POST /places/{id}/checkin` |
| bookings | `POST /bookings` · `GET /bookings` |
| devices | `POST /devices` (install_id, APNs-токен, язык) |
| analytics | `POST /events` (батч) |

### Ф1. Сервер-каркас

**[x] Ш-03. Раннер миграций**
- `db/migrate.py`: таблица `schema_migrations(version, applied_at, checksum)`; применяет
  `db/migrations/*.sql` по номеру, каждый файл в своей транзакции; падает, если checksum
  применённого файла изменился.
- `0001_init.sql`: расширения `postgis`, `pgcrypto`, `citext`; таблица `jobs`.
- DoD: миграции применяются на пустую базу и повторный запуск ничего не делает; тест на это.

**[x] Ш-04. FastAPI-каркас**
- `app/main.py`, конфиг из env (pydantic-settings), структурные логи (JSON), request-id.
- `app/db.py`: `psycopg_pool.AsyncConnectionPool`, контекст-менеджер транзакции, хелперы
  `fetch_one/fetch_all/execute` с `dict_row`. Все запросы — константы в `sql.py` модулей.
- Единый формат ошибок, `GET /health` (проверяет БД), `GET /v1/meta` (версия, мин. версия iOS).
- Локализация серверных сообщений RU/EN по `Accept-Language`.
- DoD: `make run` поднимает API, `/health` → 200; `ruff` чистый.

**[x] Ш-05. Тестовая инфраструктура**
- `pytest` + `pytest-asyncio` + `httpx.AsyncClient`; тестовая база создаётся из миграций,
  каждый тест в откатываемой транзакции.
- GitHub Actions (или локальный `make ci`): lint + тесты сервера.
- DoD: `make test` зелёный, есть пример теста API и теста SQL.

**[x] Ш-06. Очередь задач и воркер**
- `app/worker.py`: цикл `SELECT … FROM jobs WHERE run_at <= now() AND done_at IS NULL
  FOR UPDATE SKIP LOCKED LIMIT n`; ретраи с бэкоффом; регистрация обработчиков по `kind`.
- Периодические задачи (cron-подобные) — таблица/код расписания, создающие jobs.
- DoD: тест — задача ставится, выполняется ровно один раз двумя воркерами параллельно.

### Ф2. Данные мест

**[x] Ш-07. Схема мест**
- Миграция: `place_categories`, `places` (GIST-индекс по `geom`, индекс по `status`),
  `place_hours`, `place_photos`, `place_menu`, `curated_routes(+items)`, `events`.
- Сид категорий (`data/seed/categories.sql`): достопримечательности, музеи, парки, горы/природа,

- DoD: в авиарежиме открывается скачанный маршрут со всеми временами.

**[ ] Ш-43. История чатов и поездок (SSOT §11.4)**
- Боковая панель: недавние чаты (перечитать), «Новый чат», поездки.
- DoD: UI-тест. **Веха M4 → сборка в TestFlight** (с допущениями §2, со стабами SMS/LLM
  заменёнными на реальных провайдеров, если решения уже приняты).

### Ф14. Пользовательский контент и бонусы (SSOT §10)

**[ ] Ш-44. Отправка контента**
- Типы: отзыв, меню, фото, данные о транспорте, цены за вход. Фото — загрузка в S3 по
  presigned URL, сжатие на клиенте, удаление EXIF-геоданных.
- DoD: каждый тип отправляется из карточки места.

**[ ] Ш-45. Автофильтр и модерация**
- Автофильтр: правила (длина, повторы, ссылки, мат-лист RU/EN/KZ, дубликаты фото по хешу,
  правдоподобие цен) + опционально классификация LLM. Мусор → `rejected_auto`, бонус 0.
- Прошедшее фильтр публикуется сразу с пометкой «проверится позже» (SSOT §10.2), попадает
  в очередь модерации в админке; модератор подтверждает/отклоняет.
- DoD: тесты фильтра; сценарий модерации в админке.

**[ ] Ш-46. Бонусы** `[!] формула — SSOT §16.8`
- `bonus_ledger` только вставки; начисление после одобрения модератором.
- `demand_coefficients`: давность данных поля × частота попадания места в маршруты
  (временная формула в `bonus_policy.py`, коэффициенты настраиваются в админке).
- 1 бонус ≈ 1 тенге (SSOT §10.3). Трата бонусов — не делаем до решения.
- iOS: баланс и история в профиле.
- DoD: тесты начисления; нельзя получить бонус дважды за одно и то же.

### Ф15. Загруженность (SSOT §7.3) `[предложено, §2 п.5]`

**[ ] Ш-47. Собственные данные о загруженности**
- «Я здесь» (только при нахождении в радиусе места) и отчёт «людно / нормально / пусто».

### Ф16. Мероприятия и бронирования

## 10. Риски, которые держим в голове

- Нет официального GTFS по Алматы → общественный транспорт приблизительный (Ш-21).
- Обязательное пожелание без подходящего места/партнёра (SSOT §12, §16.11).
- Стоимость LLM на гостевой чат → лимиты и короткий контекст (Ш-30).
- Условия Open-Meteo для коммерческого использования (Ш-39).
- Качество OSM-данных по заведениям → ручная редактура и UGC (Ш-09, Ф14).
- Локализация ПДн в РК (Ш-51).
